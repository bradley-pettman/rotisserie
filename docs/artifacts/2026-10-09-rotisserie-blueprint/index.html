1 · Architecture

The system you're building

One backend, one database, and the phone as its first client. The web app becomes an optional second client later. It calls the same API and holds no special access to the database.

  DB[("PostgreSQL (migrations via dbmate)")]
  Shared[["Shared package: Zod schemas + TS types"]]
  Web["Web app (later, optional)"]

  Client -- "HTTPS · JSON" --> Routes
  Queries -- "SQL" --> DB
  Shared -.-> Client
  Shared -.-> Validate
  Web -. "HTTPS · JSON" .-> Routes

The shared package is what keeps the phone and the server agreeing on the shape of a recipe. Define a schema once in Zod, and the server validates with it while the app gets the TypeScript type from it.

2 · One request, end to end

"I cooked tonight's planned meal"

This is the most interesting write in the app, because it touches all three areas of the schema. It records a fact (a cook) and links it to an intention (the plan item).

sequenceDiagram

  participant App as Expo app
  participant API as API route

  participant DB as Postgres

  Z-->>API: valid input (or 400 with field errors)
  API->>DB: BEGIN
  API->>DB: SELECT name FROM recipes WHERE id = $1
  Note over API,DB: the name is copied into cooks.label as a snapshot
  API->>DB: INSERT INTO cooks (...) RETURNING id
  API->>DB: INSERT INTO cook_fulfillments (cook_id, meal_plan_item_id)
  API->>DB: COMMIT
  API-->>App: 201 { cook }
3 · The full schema

Ten tables in three areas

Recipe book

recipes · ingredients · recipe_ingredients · units · tags · recipe_tags

What you know how to make. Ingredients, units and tags are shared vocabularies that recipes point into.

Cooking history

cooks

Fact. Append-only record of what was actually made, and when. It survives deleting a recipe.

Planner

meal_plans · meal_plan_items

Intention. Editable, and it may never happen. Moving tacos to Wednesday doesn't rewrite history.

The bridge

cook_fulfillments

Which cooks fulfilled which plan items. Optional on both sides, so it's a separate table.

How to read the crow's feet: || means exactly one, |o zero or one, o{ zero or many. So recipes |o--o{ cooks says a cook may have no recipe (takeout, improvisation), and a recipe may never have been cooked.

4 · Foreign key choices

What happens when you delete a recipe

Most of the design lives in the ON DELETE rules. Each one answers the question "does this row still mean anything once the recipe is gone?"

Child rowRuleWhy
recipe_ingredientsCASCADEAn ingredient line is part of the recipe. It has no meaning on its own.
recipe_tagsCASCADEThe link goes away. The tag itself stays for other recipes.
meal_plan_itemsCASCADEA plan to cook something that no longer exists is meaningless.
cooksSET NULLYou still made it. label keeps the name readable after the recipe is gone.
Parent rowRuleWhy
ingredientsRESTRICTYou can't delete "flour" while a recipe still uses it.
unitsRESTRICTSame reason. A line saying "2 ___ flour" would be broken data.
5 · Invariants

Rules the database enforces

  • Vocabulary is stored lowercase. ingredients, units and tags each have a CHECK that name = lower(btrim(name)). Otherwise "Flour" and "flour" become two rows that ON CONFLICT (name) can't tell apart. Capitalize when you display a name, not when you store it.
  • A plan item must name something. CHECK (recipe_id IS NOT NULL OR custom_text IS NOT NULL). "Pizza night" with no recipe is valid. A blank row is not.
  • Dates are calendar days, not instants. cooked_on, planned_on and the plan range are DATE. Return them as 'YYYY-MM-DD' strings, or a time zone will shift them by a day.
  • Same four meal slots everywhere. cooks and meal_plan_items share breakfast, lunch, dinner and snack, so a cook lines up with the plan item it fulfils.
  • A recipe can list an ingredient twice. "2 cups flour, divided" plus "1 tbsp for dusting". That's why recipe_ingredients has its own id instead of a (recipe_id, ingredient_id) key.
6 · Where to start

The smaller starting schema

Five tables. That's enough for a phone app that stores, searches and shows recipes. Every table here carries over to the full schema unchanged, so nothing gets thrown away later.

cooks is included early, in a stripped-down form, because "when did I last make this?" is the first question a phone app answers well. Tags, meal plans and fulfillments come later.

Build order

  1. Migrations for the five tables. Write the SQL yourself, run dbmate up, then insert a few rows by hand in psql.
  2. Read endpoints. GET /recipes?q= and GET /recipes/:id, the second with ingredients joined in. Test with curl.
  3. Write endpoints. POST /recipes saving the recipe and its ingredient lines in one transaction. This is where the lowercase rule and the ingredient upsert live.
  4. Expo app, read-only. A recipe list and a recipe screen, pointed at your laptop's IP.
  5. Log a cook. One button, one POST /cooks. Show "last made" on the recipe screen.
  6. Add the next area. Tags, or meal plans plus cook_fulfillments, whichever you miss first.
